The project conforms to Hexagonal architecture rules

https://docs.cline.bot/customization/cline-rules


# Packages / Layers
## Domain
This is the layer that store the business logic. It should not contain any code dependent of a technical library, just
access to java.lang, java.util, (basic java standard lib packages), javax.validation, basic org.springframework (only 
core spring like @Autowired, @Component annotations)
Sub packages corresponds to business concept.
The structure of those sub package is 2 subpackages:
- model: some POJOs respecting the rules of clean architecture. A domain object needs to be valid in all 
  its lifecycle, from instance creation to garbage collection. Constructor should check all the mandatory 
  properties are there, using @NotNull annotations and explicit checks with Objects.requireNotNull.
  The getters should also precise those annotations. Setters should check the mandatory properties in the same
  as constructor. Non-mutable fields should have the final modifier. The model part is a crucial part of the
  **business logic, business rules should be implemented directly in domain objects when possible (ex: for a 'state'**
  property, the workflow should be checked in the setState() setter, constructor should init state with the initial 
  state) 
- services: implements the business operation that cannot be implemented in domain objects. 
- ports: interface with suffix Port corresponding to an adapter from a deeper layer (like infrastructure). 
  The implementation of these ports (adapters) are located in the infrastructure layer with the naming convention 
  XXXAdapter (e.g., FilePort -> FileSystemFileAdapter, UserRepository -> JdbcUserRepositoryAdapter).
This layer cannot access any other layer but can be access from all the other layers.

## Application
This is an applicative layer whose role is to combine different parts of the domain layer.
It can only access the domain layer.
It shares the same rules as the domain layer except the port subpackage that is not relevant here.

## Exposition
This is the layer containing the rest endpoints. 
It contains subpackage for every different business categories. (those categories should match those in domains or 
application layers)
Those subpackages contains all the same structure
- rest: the REST controllers implemented in spring MVC. Note that classes should implement some interfaces 
  generated by OpenAPI. Some methods can rarely be fully implemented without OpenAPI generation (when those 
  endpoints are not supposed to be public but for debugging purpose)
- model: the DTOs used by the controllers. Most of those DTOs will be generated by OpenAPI
It can access domain and application layers

## Infrastructure
This is the layer with the technical code doing the implementation.
It contains some subpackages corresponding to technologies used (ex: rest for external REST calls, postgres for DB
access, security.oauth2 for authentication...)
Those subpackages are structures with those subpackages:
- adapter: implementation of some ports declared in domain layer. The naming convention is XXXAdapter 
  (e.g., FilePort -> FileSystemFileAdapter). Note that signature should only use objects of the
  domain layer since the interface is defined there.
- model: contains object manipulated by the infrastructure layer and mappers (implemented with mapstruct lib) to 
  convert those objects to upper layer model objects (domain mainly)
It can access domain and application layers
